---

## 1. Propósito deste documento

Este arquivo existe para orientar a criação da versão 2.0 do portfólio profissional de Antonio Silos.

Ele **não é um prompt de implementação** e não deve ser interpretado como uma ordem para reescrever imediatamente o projeto. Sua função é registrar o contexto profissional, a hierarquia das informações, os projetos que devem ou não aparecer, a direção de design e os critérios que definem uma apresentação profissional coerente com o momento atual da carreira.

Antes de qualquer refatoração, o agente responsável pela implementação deve auditar os arquivos atuais e confrontar a implementação existente com este documento.

Quando houver conflito entre versões antigas do portfólio e este arquivo, **este arquivo prevalece em questões de posicionamento, conteúdo e decisões de produto**.

Para detalhes sobre funcionalidades do Equilibrium, o **repositório atual do Equilibrium no momento da implementação** deve ser tratado como fonte técnica de verdade. Não apresentar como concluída nenhuma funcionalidade que não possa ser confirmada no código atual.

## 2. Objetivo da V2

A V2 deve transformar o portfólio atual de uma apresentação com aparência de projeto pessoal/estudantil em uma presença profissional clara, madura e confiável.

O objetivo **não é apenas modernizar o CSS**.

A evolução deve contemplar:

- posicionamento profissional;
- arquitetura da informação;
- narrativa;
- hierarquia visual;
- apresentação dos projetos como evidência de competência;
- experiência do usuário;
- responsividade;
- acessibilidade;
- performance;
- SEO básico;
- organização e manutenção do código.

Ao final, o site deve parecer o portfólio de um desenvolvedor em início de carreira com experiência profissional real em tecnologia, capacidade prática de construir software e compreensão de sistemas e problemas de negócio.

A V2 **não deve tentar simular senioridade**.

## 10. Equilibrium — papel no portfólio

### Definição

O Equilibrium deve ser apresentado como:

> Aplicação web multiusuário para gestão de pacientes, agendamentos e sessões de terapia à distância.

Evitar definir o projeto como “SaaS” enquanto o produto ainda não possuir uma operação que justifique esse posicionamento.

### Tecnologias principais

- Python
- Flask
- MySQL
- mysql-connector-python
- HTML5
- CSS3
- JavaScript
- Jinja2
- bcrypt
- python-dotenv
- Flask-WTF / CSRFProtect
- Flask-Limiter
- pytest

No resumo visual do portfólio, não é necessário exibir toda essa lista. Priorizar **Python · Flask · MySQL · JavaScript** e usar as demais tecnologias dentro do case quando ajudarem a explicar arquitetura, segurança ou testes.

### Capacidades já demonstradas pelo projeto

O case pode explorar as funcionalidades e decisões já documentadas no repositório atual, incluindo:

- autenticação com hash de senha utilizando bcrypt;
- perfis `ADMIN` e `TERAPEUTA`;
- contas com status ativo/inativo;
- invalidação da sessão quando um usuário é desativado;
- autorização baseada no estado atual registrado no banco;
- administração de contas de terapeutas;
- comando CLI para criação segura do primeiro administrador;
- gerenciamento de pacientes;
- isolamento de pacientes por `terapeuta_id`;
- normalização e unicidade de telefone dentro da carteira de cada terapeuta;
- gerenciamento de agendamentos;
- duração configurável de sessões;
- seleção de música;
- edição, cancelamento e histórico paginado de agendamentos;
- sessões terapêuticas com token de acesso exclusivo;
- cronômetro baseado em timestamps do servidor;
- persistência do estado da sessão após recarregar a página;
- encerramento automático da sessão;
- controles de reprodução de áudio;
- dashboard com indicadores e informações recentes;
- persistência em MySQL;
- separação entre rotas Flask e camada de serviços;
- templates e arquivos estáticos organizados separadamente;
- proteção CSRF;
- rate limiting no login;
- queries SQL parametrizadas;
- variáveis de ambiente para credenciais e segredos;
- health check da aplicação e do banco;
- testes automatizados com pytest, Flask test client, mocks e monkeypatching.

### Linguagem de segurança

Segurança é uma dimensão real do projeto e pode receber destaque no case, desde que a linguagem continue verificável e proporcional.

Medidas documentadas incluem:

- bcrypt para senhas;
- proteção CSRF;
- rate limiting no login;
- queries SQL parametrizadas;
- autorização no servidor;
- verificação atual de perfil e status diretamente no banco;
- invalidação de sessões de usuários desativados;
- isolamento de dados por terapeuta;
- variáveis de ambiente para segredos e credenciais;
- mensagens genéricas de falha na autenticação;
- tokens de acesso gerados de forma segura.

Evitar afirmações vagas como:

- “sistema totalmente seguro”;
- “segurança de nível empresarial”;
- “aplicação inviolável”.

Preferir explicar concretamente quais controles foram implementados e, quando pertinente, quais cenários são cobertos por testes automatizados.

### Status

O Equilibrium deve ser apresentado como **projeto finalizado em seu escopo atual e ativo como projeto de portfólio**.

Ele continua aberto a evolução e possui um roadmap de melhorias futuras, mas isso não significa que o projeto esteja incompleto.

É importante distinguir:

- **funcionalidades existentes e concluídas**, que podem ser apresentadas normalmente;
- **melhorias futuras**, que devem aparecer apenas como roadmap ou evolução planejada;
- **demo online**, que só deve ser apresentada como disponível quando houver uma URL pública funcional.

Não usar frases como “projeto em desenvolvimento” para definir o status geral do Equilibrium.

### Repositório

O repositório do Equilibrium já possui estrutura de apresentação e documentação adequadas para servir como evidência técnica do projeto.

O repositório contém atualmente:

- README em português, inglês e francês;
- documentação da visão geral e das funcionalidades;
- instruções de instalação e reprodução local;
- `.env.example`;
- `requirements.txt` e `requirements-dev.txt`;
- schema completo do banco de dados;
- diretório de migrações;
- comando CLI para criação do primeiro administrador;
- endpoint de health check;
- suíte de testes automatizados;
- screenshots;
- explicação das principais decisões de arquitetura;
- seção dedicada à segurança;
- roadmap;
- licença MIT para o código-fonte;
- aviso específico excluindo os assets de áudio da licença MIT.

O portfólio pode direcionar recrutadores para esse repositório como uma fonte técnica real do projeto.

Ao descrever o Equilibrium no portfólio, o README e o código atual do repositório devem continuar prevalecendo sobre versões antigas deste documento.

## 19. Internacionalização

A implementação atual de tradução pode ser refatorada.

Com três idiomas e mais conteúdo, evitar concentrar grandes blocos de tradução no mesmo arquivo que contém toda a lógica de interação da página.

### 3. Clareza antes de efeitos

Design deve organizar e comunicar, não disputar atenção com o conteúdo.

### 4. Precisão antes de marketing

Não inflar projetos, competências ou responsabilidades.

### 5. Evolução, não personagem

O objetivo não é inventar uma versão mais experiente de Antonio. É apresentar de maneira profissional o desenvolvedor que ele **já é hoje** e deixar clara a direção em que está evoluindo.
